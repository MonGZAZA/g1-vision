# 2.3 Vision: Human Detection & Recognition — research notes

2026-11-13. Background for the 2.3 session of `student/STUDENT_GUIDE.html`. **Implemented the same day: see
[`../vision/README.md`](../vision/README.md).** This file
proposes what to build and what to measure. Facts marked *(verify)* come from secondary sources only.

## 1. What 2.3 has to deliver

Vision does **not** decide what the robot does. It reports what it sees; a behaviour state machine
(idle → greet → listen → answer → point, see the guide's integration section) turns events into calls to the
existing API (`/api/intro`, `/api/stop`, …).

| Need | Signal | Proposed threshold (to tune) | Reaction (existing API) |
|---|---|---|---|
| Someone approaches | tracked person, distance < 2.0 m, facing, closing speed > 0.2 m/s *or* dwelling | 2 frames in a row in the zone + facing ≥ 0.5 s | `POST /api/intro` |
| Someone stops in front | distance < 1.2 m for > 2 s | — | start listening (2.2) / offer help |
| Safety near the arms | **any** point/person < 1.0 m on the arm side | no debounce on the way in, 2 s on the way out | block `/api/point`; `POST /api/stop` during motion |
| Where the person is | bearing (deg, robot frame) | smoothed, ±15° cap | later: small waist-yaw turn toward the person |
| Person leaves | track lost or > 3 m for > 3 s | — | back to idle; cooldown |
| Recognition (optional) | staff / returning visitor | opt-in only | no greeting for staff, short greeting for a returning visitor |

Proposed event contract (HTTP on port 8107, plus `GET /state` with the current tracks):

```json
{"type":"person_near","t":1731480000.12,"id":3,"distance_m":1.6,"bearing_deg":-12,
 "facing":true,"speed_mps":-0.4,"dwell_s":0.8,"source":"d435i","n_people":2}
```
Types: `person_near`, `person_dwell`, `person_left`, `too_close` (side: left/right/front), `clear`.
Coordinates in the robot frame: x forward, y left, bearing positive to the left (same as the waist yaw sign used by
`pointing.py` — check before integrating).

## 2. Sensors we actually have

From our own hardware notes (`exp02/HANDOFF.md`, `exp04/`), not from catalogues:

| Sensor | Where | How we can read it today | Good for |
|---|---|---|---|
| **Intel RealSense D435i** (head) | USB on PC2 (Jetson, .164) | colour: Unitree's `unitree-camera-server` on PC2 :8000 `/capture` (base64 JPEG, low rate); depth: our `exp04/g1/deploy/camera_streamer.py --depth-only` (:8093, keeps Unitree's colour service running) | detection + **metric distance from depth** (no size guessing), facing |
| **Livox MID-360** (head, mounted upside down) | .120 → PC2; `exp04` `lidar_relay.sh` copies packets to the laptop | already used for FAST-LIO2 in exp04 | **360° proximity / safety** (behind and beside the robot, where the camera is blind) |
| Laptop webcam | `/dev/video0…3` on this laptop | OpenCV | development, starter exercise |

Notes:
- D435i: depth is reliable roughly 0.3–3 m, which covers the whole greeting zone (≤ 2 m). Its field of view is
  about ±43° horizontally for depth, less for colour, so a person standing beside the arm is **outside** the camera
  view. That is why the arm-safety check should use the lidar, not the camera.
- MID-360: vertical FoV −7°…+52°, min range ~0.1 m *(verify)*. Mounted upside down on the head, so it mostly looks
  **down and around**: at 1 m it sees legs and torsos all around the robot — exactly the arm-safety zone. A simple
  rule (points 0.2–1.8 m above the floor, inside a 1 m ring, minus the robot's own body box) needs no learned model.
- PC2 is **shared with another team** (their SLAM docker, Unitree's camera service). Rules from exp02/exp04 apply:
  never change their setup; our helpers leave a note and `stop` restores everything. `camera_streamer.sh start`
  (colour from ours) stops Unitree's service, so only with the robot owner's OK.
- Compute on PC2: Jetson Orin NX 16 GB per Unitree's developer docs (100 TOPS per resellers, *verify*), Ubuntu 20.04,
  Python 3.8. Running our models there is possible later, but the first version should run on the laptop
  (RTX 4060 8 GB; exp05's AI service uses ~4 GB today, so ~3 GB is left for 2.2 ASR + 2.3 vision together).

**Sim:** the MuJoCo sim has no people. Detection itself cannot be tested there; use the laptop webcam and recorded
video. For the state machine, write a fake vision source (keyboard or a scripted timeline that emits the same JSON
events) so the behaviour layer can be tested in the sim without a camera.

## 3. Pipeline

```
frame (webcam / D435i colour + aligned depth)
  → person detector (boxes)            ─┐
  → tracker (stable IDs)                │ 10–15 fps is enough for walking speed
  → per track: distance, bearing,       │
     facing, speed, dwell               │
  → event logic (zones, hysteresis,     │
     cooldown per ID)                  ─┘
  → events → state machine → /api/intro …
lidar (MID-360, 10 Hz) → ring check around the robot → too_close / clear  (independent, simpler, safety path)
```

### 3.1 Detection
| Option | Licence | Notes |
|---|---|---|
| **MediaPipe Pose Landmarker** | Apache-2.0 (framework; check the model card) | **Already installed in `ai/.venv`** (mediapipe 0.10.21, used by the wai video tool). CPU, gives 33 landmarks → shoulders/nose for facing. `num_poses` defaults to 1; set it to e.g. 4. No track IDs; reported to degrade with many people *(verify)*. Best for the starter exercise. |
| RTMDet / RTMPose / RTMO via **rtmlib** | Apache-2.0 (rtmlib; check model weights) | onnxruntime only, no mmcv. RTMO is a one-stage multi-person pose model, faster than top-down when > 4 people. Benchmarks exist for Orin NX (TensorRT). Good second step. |
| RF-DETR | Apache-2.0 (core models; the largest "Plus" checkpoints have their own licence) | modern detector, strong accuracy; only boxes. |
| YOLOX | Apache-2.0 | older but solid, easy ONNX/TensorRT. |
| Ultralytics YOLO (v8/11/26) | **AGPL-3.0** or paid enterprise | easiest to use, but AGPL would force the whole exp05 code open under AGPL if distributed/served. Fine for a private experiment; avoid for anything the shop would deploy unless licensed. |

Recommendation: **MediaPipe for the starter and the first demo** (zero install), then **rtmlib (RTMDet-person or
RTMO)** when multi-person tracking at the entrance becomes the bottleneck.

### 3.2 Tracking
Needed so "greet once per person" and "dwell 2 s" work. ByteTrack (MIT) is the standard; the `supervision` package
ships an implementation (`sv.ByteTrack`) and converts MediaPipe results (`sv.KeyPoints.from_mediapipe`). With depth,
a simple nearest-neighbour tracker on (x, y) in metres is also enough for ≤ 5 people.

### 3.3 Distance and bearing
- **D435i:** median of the aligned depth inside the torso region (between the shoulder and hip landmarks, or the
  middle 30 % of the box). Median rejects background pixels. Bearing = atan of the pixel x through the intrinsics.
- **Webcam (no depth):** distance ≈ f · W / w_px with shoulder width W ≈ 0.40 m (adult; wrong for children and side
  views) or head height. Expect ±20–30 %; good enough for the exercise, not for safety.
- Smooth with an exponential filter or a 1D Kalman filter; speed = d(distance)/dt from the filtered value.

### 3.4 Facing / intention to interact
Cheap cues, in order of cost: a frontal face is found (OpenCV **YuNet**, MIT, fast on CPU, 5 landmarks); both
shoulders visible and shoulder width ≈ expected for that distance (torso square to the camera); nose between the
eyes (head yaw from landmarks). Combine: *approaching OR dwelling* AND *facing* for ≥ 0.5 s.

Research on this exact problem (useful for the discussion): Bohus & Horvitz on predicting engagement in open-world
settings (Microsoft Research), work on F-formations (groups standing in a ring — greet the group once, not each
member), and *Self-Supervised Prediction of the Intention to Interact with a Service Robot* (arXiv 2309.07477), which
tracks people within 4 m and uses torso and head orientation, learning labels automatically from whether an
interaction happened afterwards. That last idea fits us: log tracks + "did they ask a question" and tune thresholds
from the log (track numbers only, no images).

### 3.5 Arm safety (lidar)
Independent of the camera and much simpler: crop the MID-360 cloud to a ring 0.25–1.0 m around the robot, 0.2–1.8 m
above the floor, remove the robot's own arms (forward kinematics from `rt/lowstate`, or a fixed exclusion box), count
points per sector (left / front / right). Above N points → `too_close`. Needs the floor height and the lidar's
upside-down transform, which exp04 already solved (`exp04/README.md`, alignment). Today `/api/point` would then be
refused while `too_close` is set; this is a server change and must go through the `server.py` owner.

## 4. Recognition (optional) and the law

- Thailand's PDPA, section 26: biometric data (face recognition is the standard example) is **sensitive personal
  data**; it needs **explicit consent** unless an exception applies. Commentary says signage / "consent by entering"
  is not enough for this *(commentary, not a PDPC ruling — verify with the shop's legal contact)*.
- Detection, distance and tracking without storing images or identities is far lower risk: process in memory, store
  no frames, log only numbers (track id, distance, times).
- Ways to "recognise" without faces:
  - **Staff:** uniform colour, a badge, or an ArUco/QR tag on the badge (OpenCV aruco). Reliable, no biometrics.
  - **Returning visitor within one visit:** keep the track ID (and, if needed, an appearance embedding) **in RAM
    only**, forget after e.g. 10 minutes. Avoids greeting the same person twice when the track is briefly lost.
- If face recognition is still wanted (opt-in gallery only): InsightFace **code** is MIT but its **pretrained models**
  (buffalo_l, antelopev2) are non-commercial research only. Permissive pairs reported: YuNet (MIT) + SFace (OpenCV
  Zoo, Apache-2.0) or AuraFace (Apache-2.0) *(verify each licence file)*.

## 5. What to measure (targets to agree on)

| Metric | How | Proposed target |
|---|---|---|
| Missed greeting | staged walk-ups by group members, 50 trials | ≤ 5 % |
| False greeting | passers-by crossing at 1–3 m without looking; posters; people behind glass | ≤ 1 per hour of entrance video |
| Double greeting | same person stays 1 min / steps back and returns | 0 within the cooldown |
| Distance error | tape marks at 0.5 / 1 / 1.5 / 2 / 3 m | ≤ 10 cm with depth; ≤ 25 % webcam |
| Latency | person crosses the 2 m line → `/api/intro` sent | ≤ 300 ms |
| Arm safety | person at 0.8 m beside the arm, every direction | 100 % `too_close`, < 100 ms |
| Load | GPU MB, CPU %, fps with TTS + LLM + ASR running | fits in ~1 GB GPU, ≥ 10 fps |

Test footage from the real entrance needs the shop's permission; stage tests with group members first.

## 6. Suggested plan for the 2.3 group

1. **Starter (day 1):** webcam + MediaPipe (`ai/.venv`), distance from shoulder width, print an event < 2 m, call
   `/api/intro` with a 30 s cooldown (the exercise in the guide). Own folder, e.g. `exp05/vision/`.
2. **Tracker + events:** add ByteTrack, dwell, facing (YuNet), the JSON event contract on :8107, a fake-event mode
   for the state-machine group. Ship `tools/vision_check.py` (recorded clips → expected events), like the other
   `*_check.py`.
3. **Robot camera:** D435i colour (Unitree :8000) + depth (`camera_streamer.py --depth-only`) over the robot network;
   depth distance; measure the colour frame rate we actually get from `/capture` — if it is too low, ask the robot
   owner about running our streamer for both streams.
4. **Lidar safety ring:** from exp04's relay; `too_close` → server refuses pointing (with the `server.py` owner).
5. **Later / optional:** move inference to PC2 (TensorRT), staff badges, intention model from logs, small torso turn
   toward the person.
